# The end-to-end collaboration flow, after refutation

Source: workflow `wf_a631b9b8-06c`, 13 agents, six staff groups each drafted then
refuted against BrotherSBE's real limits, plus a synthesis following one change
(a product-master field consumed by order, cart and search) across two timezones.
Anonymised: no company, no names.

The refuters removed a great deal. Read this as what SURVIVED, not as a pitch.

## The seams where work is lost today

- THE TIMEZONE SEAM, and it is the one that matters. Tokyo evening to offshore night, and 06:00 JST back to Tokyo. Today the artifact that crosses is a sentence in a chat window, which nobody can query later and which cannot settle the question of what was finished, what was half done, what was never started and what question was left open. With BrotherSBE two files cross instead: the work brief (byte-identical JSON carrying scope, mustNotTouch, dependencies, acceptance, verificationCommands, stopConditions and baselineCommit) going out, and 12-handover.json coming back, with acknowledge refusing on a stale record and refusing a self-handover. What crossing this seam still does NOT do: it notifies nobody, wakes nobody, enforces no response time, and writes openQuestions, decisions and requiredAccess EMPTY for a human to fill. Ownership moves in a JSON file two people agreed to read, not in any system. And the reason it is the most important seam is unchanged by any of this: the two BAs and the Integration Manager who can answer intent questions are asleep for the whole offshore build window, so a stop condition converts an eight hour stall into a written escalation, and nothing converts it into an answer.
- THE PIMCORE ADMIN UI TO GIT SEAM. A field retyped and saved in the Pimcore admin UI in the Japan afternoon crosses no seam at all: no diff, no pull request, no Jenkins run, no SonarQube decoration, no reviewer, no gate. Every BrotherSBE check, detector and gate reads a git diff, a JSON file or a markdown file, and nothing notices the omission. The artifact that has to cross is an exported class definition committed under a path a detector matches, produced by an export job the team builds and BrotherSBE does not ship. Until that job exists, everything downstream of this seam is inert for the CONTENT group, and the honest answer is that BrotherSBE does nothing for them. Even after it exists, only the SHAPE half crosses: the Pimcore publish of the values still reaches production without traversing Development, Staging or Pre-Production.
- THE CONTENT TO PRODUCT SEAM, where the system of record is decided. Product master in Pimcore, price in the Product service SQL Server tables, a derived Elasticsearch index, a Redis cache, editorial copy in Strapi that also carries product-shaped fields, read by three client apps. The artifact that crosses is 05-data-model.md, and the datamodel check FAILs any entity with no named system of record and any relationship with no cardinality. What it cannot do is tell a correct answer from a confident wrong one: writing Strapi where the truth is Pimcore passes. Cardinality is the specific trap on this business, because product variant to SKU to retailer contract price list is many-to-many and gets implemented as one-to-many by whoever writes the sync first, discovered when a retailer sees a price from someone else's contract.
- THE PUBLISHER TO CONSUMER SEAM inside the change itself. The Pimcore field feeds ProductSync, which writes SQL Server, which Order Service and Cart Service read and which the Elasticsearch index is derived from. Nothing here reads a .NET DTO, an Ocelot route file, a RabbitMQ binding, a message shape, a dead letter policy or a Helm chart, and converge cannot even classify the .cs file that implements the consumer. There is no consumer impact analysis and no deploy-ordering check for a publisher and its consumer. The only artifact that crosses this seam is the handoff row a human typed into 02-process.md, which is unchecked prose. This seam is where the two blind spots overlap: the impact detectors read path names, so a queue contract change inside a C# service whose path carries no trigger word is invisible, and the silent-failure linter cannot read that file either.
- THE REPOSITORY TO NON-REPOSITORY-USER SEAM. Contractor Operations Consultants, the CS Specialists and most of the commercial group have no Bitbucket account, and the dossier lives in the repository. Their own words go into 01-purpose.md and the acceptance rows go into 07-verification.md, and they cannot open either. The artifact that has to cross is a published readable copy, on merge, to somewhere without a repository account. BrotherSBE ships nothing that does this, and until somebody builds it the crossing is a BA emailing files.
- THE MERGE AND REBASE SEAM. Receipts and gate verdicts are commit-bound and strict about it, and this repository enforces linear history. A receipt minted on a feature branch tip FAILs at the merge commit, and a covered file rewritten after the run (a checkout, a formatter, even with identical bytes) invalidates it. The artifact that crosses is a receipt regenerated by the pipeline on the post-rebase head, written outside the tree it covers, because a receipt written into that tree makes it dirty and demotes the next one to advisory.
- THE CI TO PRODUCTION-APPROVAL SEAM. The artifact that crosses is an evidence pack: bin/sbe status . --team plus the four gate verdicts re-run against the release commit, archived and written into the build description immediately before the Jenkins input step. Two hard limits on this crossing. The Jenkins input approval and the BrotherSBE approval gate are two different approvals, and the gate verdicts in the pack are the same verdicts that already passed at PR time, so re-running them proves the commit is unchanged, not that Staging behaved. And for a T0 promotion, which is most of them, the pack is close to empty and the approver is back to reading a build number.
- THE PRODUCTION TO NEXT-ITERATION SEAM. The artifact that should cross is a commit sha: Sentry release name equal to the commit that Jenkins already pushes, and design/<change>/ reachable from that sha, so an incident walks back to a commit and a commit walks back to a dossier and its ADR. Nothing computes or enforces this. BrotherSBE reads no Sentry, no Prometheus, no Grafana, no CloudWatch, no ELK and no Alertmanager, performs no post-deploy verification, and has no answer to the question this team actually asks, which is whether the fix is live in production.

## The CI and CD stages to add, in order, advisory first

- ADVISORY PHASE, stage 1 of the PR job, sbe-triage. Runs on every PR open and every push to the PR branch, wrapped in catchError(buildResult: 'SUCCESS', stageResult: 'UNSTABLE'). Command: bin/sbe impact . --base origin/master (no --intake, no --strict). Purpose is to print a tier floor from path names and export it as a Jenkins variable that later stages gate on with when{}. This stage exists so a T0 change costs nothing: BrotherSBE ships no pipeline file, no when{} condition and no skip logic, so this branching is the Full Stack lead's work. Prerequisites that bite on day one: python3 at 3.9 or newer on the agent (a .NET SDK image does not have it, so change the image or route the SBE stages to a dedicated agent label), and a non-shallow clone with tags, because the approval gate later reads commit trailers and signatures.
- ADVISORY PHASE, stage 2, sbe-install-verify. Command: sh scripts/verify-install.sh. Confirms the checked-out plugin matches the manifest shipped with its pinned ref, in both directions. It catches drift and accident. It is not a defence against somebody who edits the manifest too. Keep it wrapped for the first sprint like everything else.
- ADVISORY PHASE, stage 3, sbe-score, the only SBE stage most pull requests on this estate will ever feel. Command: python3 tools/sbe_score.py --strict --strict-soft . run in parallel with the existing SonarQube stage and never replacing it. Verified at tools/sbe_score.py:655, SCANNABLE is (".py", ".sql", ".swift", ".rb", ".js", ".ts", ".go"). There is no .cs, so the six .NET services, the five queue processors and the four cron jobs are outside it. There is no .tsx and no .jsx either, so confirm the real extensions in the shop and portal repositories before promising the front end anything. A run that opened no file is NO-DATA naming why, never clean. Never soften this stage with || true or set +e: a discarded exit code is the exact defect class this linter exists to catch.
- CONDITIONAL PHASE, stage 4, sbe-impact-strict. Runs only when stage 1 printed a floor above T0. Command: bin/sbe impact . --base origin/master --intake design/<change>/00-intake.json --strict. Catches a change touching helm/, charts/, k8s/, kubernetes/, .tf, .tfvars, docker-compose, a Jenkinsfile, a production-config path, a path containing rabbitmq, or an exported schema under schemas/, that was declared T0. It reads PATH NAMES, not code. It may raise a tier and may never lower one, and it reports consumers under unmeasured.
- CONDITIONAL PHASE, stage 5, sbe-design. Runs only at T2 and T3. Command: python3 tools/sbe_design.py --strict design/<change>, then bin/sbe plan design/<change>. Fails a shipped-template file left in place, an ADR without two distinct rejected alternatives and a flip condition, an entity with no system of record, a relationship with no cardinality, a diagram node tracing to no declared entity, and an empty plan. It checks that the artifacts exist and are structurally complete, never that they are true, and a dossier written after the code passes identically. Leave SBE_DOSSIER_ROOT UNSET on these repositories: a declared root holding no dossier is a FAIL by design, which turns every routine T0 change red.
- CONDITIONAL PHASE, stage 6, sbe-gate. Runs only where a dossier exists. Two commands in one stage, in this order: gpg --import of the approver public keyring fetched with the same Vault step the deploy already uses, then python3 tools/sbe_gate.py --strict design/<change>. Without the imported keys git reports %G? = E and every signed approval reads NO-DATA. A self-generated SSH signing key reports U, also NO-DATA. The keyless Reviewed-in: <Bitbucket PR id> path is NO-DATA because nothing resolves the id. On this estate the ONLY passing approval path is a host-verified signature carrying an Approved-by trailer naming somebody other than the author and committer, so self-approval fails. Public keys are not secret: Vault here is central distribution and rotation, not confidentiality. Note the exit-code fine print before relying on this stage: --strict exits nonzero on FAIL, and a NO-DATA verdict prints and exits 0, so a change that declares no migration receipt, no approval trailer and no numbers manifest produces three NO-DATA lines and a green build.
- CD PHASE, stage 7, sbe-evidence on the merge-to-master job, before auto-deploy to Staging. Commands: SBE_CI_RUN_ID=$BUILD_TAG bin/sbe evidence run --check <id> --kind gate --out <a path OUTSIDE the tree the check covers> per registered QC suite, then bin/sbe evidence verify per receipt. Regenerate on the post-rebase head, because a pre-rebase receipt FAILs at the merge commit under this repository's linear history rule. Each suite needs a .sbe/checks.yml entry that QC writes and maintains, and editing that entry invalidates receipts minted before the edit. Understand the ceiling: the printed level is CI-CLAIMED, which means a run id was recorded on a clean tree and nothing verified who set it. Any laptop exporting the same variable gets the same label; the protection is that Jenkins is the only place the team sets it.
- CD PHASE, stage 8, sbe-converge, immediately before auto-deploy to Staging. Command: bin/sbe converge design/<change> --base <the commit the design was implemented from> --head $GIT_COMMIT. Compares the diff to the approved dossier across scope, contracts, data, architecture and verification, and there is no force flag. Its source extension set contains no .cs, no .tsx and no .jsx, so on a .NET plus modern front end estate a large share of the diff is reported as unmeasured rather than as a verdict. It has nothing to say about a change that never carried a dossier.
- CD PHASE, stage 9, sbe-promotion-pack, immediately before the existing input step with its one hour timeout. Commands: re-run python3 tools/sbe_gate.py --strict design/<change> and bin/sbe status . --team against the release commit, archiveArtifacts the output, and write the blocker-first summary into currentBuild.description so it sits on the same page as the Proceed button. BrotherSBE assembles the pack and exits. It never calls input, never approves, never deploys, never learns what was clicked, and cannot see or extend the one hour clock.
- ENFORCEMENT, which is not a stage but the step that makes the stages matter. Unwrap catchError one stage at a time in the order score, impact, design and gate, converge, after two sprints of reading real verdicts against this codebase's own idioms. Then a Bitbucket admin binds a merge check of the class 'minimum successful builds on the source commit' to the SBE build status key, on top of the existing minimum two reviewers, Tech Lead approval, linear history and no force push. What that merge check CAN require: a green named build key on the exact source commit. What it CANNOT do: read the difference between FAIL and NO-DATA, require that a named evidence artifact exists, or compare an approver identity against the commit author. Check names differ between Bitbucket Cloud and Data Center, so confirm them in your own instance. Do NOT put bin/sbe work check in the blocking path: a developer who never registered gives it nothing to read. And decide the hotfix/xxx path before enforcement, not during a 03:00 JST outage, because a gate that blocks an incident fix gets waived once and then quietly deleted.

## Rollout for this team

- WEEK 1, no tooling, no pipeline, one number. Take the last four weeks of real requests and score each one with python3 tools/sbe_intake.py on a laptop. Publish the T0/T1/T2/T3 mix. This is the smallest possible first step and it is the one that decides whether to continue: the entire defence of this method is that T0 owes nothing and is the common case, and nobody has measured that on this team. If the mix skews to T2 and T3, the two Business Analysts become the bottleneck for the whole pipeline and the answer is to stop here or to re-argue the tier boundaries first. Also settle two access questions in the same week, before they become gaps in a later report: do the offshore QC engineers have Claude Code and a repository checkout, and where does BROTHERSBE_VAULT point on each machine and agent (it is unset by default, nothing syncs it between the two sites, and bin/sbe doctor reports NO-DATA on it by name).
- WEEK 2, the timezone handover only, on one change, nothing else. The PM mints a work brief per task with sbe work brief --json and the night shift opens its shift on that instead of a scrollback. At end of shift the night dev runs sbe handover prepare and the Full Stack lead runs acknowledge or reject in the morning. No Jenkins, no gates, no dossier. This works on day one because it is only files in git read at a specific commit. ## What this does NOT fix

- It does not shrink the timezone. sbe handover records that a named human acknowledged ownership at a specific commit and refuses a stale or self-handover. It notifies nobody, wakes nobody, enforces no response time, and reject leaves the work with the outgoing owner. The two BAs and the Integration Manager are still asleep during the whole offshore build window, so an ambiguity that needs their judgment is still an eight hour wait. What changes is that it becomes a written escalation instead of an undocumented guess.
- It blocks nothing on its own. Every gate is a command that prints a verdict and, with --strict, exits nonzero. Three separate pieces of the team's own wiring sit between a FAIL and a stopped merge: a Jenkins stage they write, a Bitbucket merge check an admin binds, and the branch permissions they already have. BrotherSBE ships no CODEOWNERS, no branch protection, no merge checks and no CI configuration, and its reference workflow is GitHub Actions, which is unusable here. Until those stages exist, adopting it changes what people write, not what CI does.
- It cannot see absent evidence, only declared evidence. The migration gate returns NO-DATA with the literal reason "no migration in this change, or no migration-receipt.json" and cannot tell those two apart. Nothing detects that a change NEEDED an approval, a receipt or a dossier. Worse for anyone reading a clean run as safety: --strict exits nonzero only on FAIL, so a change that declares nothing at all produces NO-DATA lines and a green build. NO-DATA is never a pass as a verdict and is not a block as an exit code.
- It does not read C#, which is most of this estate. The silent-failure linter's scannable set is pinned at tools/sbe_score.py:655 to .py .sql .swift .rb .js .ts .go. No .cs, so Identity, Product, Customer, Order, User, Cart, the five queue processors and the four cron jobs are invisible to it. No .tsx and no .jsx either, so if the shop and portal apps are React it reads almost none of the front end. converge and the impact detectors cannot classify a .cs file either, so a .NET change lands in an explicitly unmeasured category rather than a verdict. SonarQube stays the only automated reader of the backend, and no configuration closes this.
- It proves nothing about whether two derivations are independent. The numbers gate proves two texts differ beyond case, whitespace, comments and trailing punctuation, and that two transcribed figures match. It executes no query, has no database connectivity and cannot tell a transcribed number from an invented one. Two counts taken downstream of the same broken ProductSync agree and are both wrong, and two reads of the same stale Elasticsearch index pass. On pricing, rebate and reconciliation work that is a live exposure, not a theoretical one.
- It cannot see Pimcore, Strapi, Klaviyo, Voucherify, Branch.io or LINE Connect. Everything reads a git diff, a JSON file or a markdown file. A field saved in the Pimcore admin UI, a campaign built in Klaviyo, a voucher rule, a deep link, a content-type published from Strapi: none of them pass through a diff, so none gets a design phase, a gate, a linter or a receipt, and nothing notices the omission. A large share of what Sales and CS log as bugs is product data or content, not code. Say this on day one, not after a miss.
- The data model check verifies that a system of record is NAMED and a cardinality is STATED, never that either is correct. Writing Strapi where the truth is Pimcore passes every check that ships. The same holds for the ADR: the shape is checked (two distinct rejected alternatives, a flip condition present), the judgment is not. Nothing reads 01-purpose.md, 02-process.md, 04-technology-map.md or 07-verification.md for content at all, so a thin dossier written to clear the gate clears the gate, and converge then compares the diff against that thin thing.
- The tier is computed from five answers a human typed. The rule is fixed and unarguable; the inputs are checked against nothing at intake time. A BA or a Marketing lead who answers no to the money or personal-data question gets T0 and owes nothing. sbe impact can raise a tier later, never lower one, but it reasons from path names after code exists: its money detector matches pricing, discount and invoice, not the bare word price, so PriceList.json raises to T2 and no further, and a Klaviyo sync written inside existing service code may trip nothing at all.
- There is no write fence for humans. The scope comparison lives in a Claude Code PreToolUse hook whose own rule is fail open, loudly, so it binds nobody typing in Rider, Visual Studio or VS Code, and nothing binds git apply or a shell redirect. sbe work start refuses a taken branch, a taken worktree path and a re-opened task id, and never compares file scopes between two different tasks. Two Japan front end developers and the Night Dev FE holding the same cart components get a registry a human reads, not a refusal.
- It never gets apply rights on production. It cannot deploy, cannot approve, cannot merge, cannot publish or unpublish a Pimcore object, cannot trigger a re-sync or a reindex. It drafts the command and its rollback for a human to run. The Jenkins input approval and its one hour timeout are exactly as human as before, and BrotherSBE never learns the click happened. No receipt describes production state, so the question CS actually asks, is it live and is it fixed, has no answer here today or after wiring.
- It reads no telemetry and does nothing after the rolling update starts. No Sentry, Prometheus, Grafana, CloudWatch, ELK or Alertmanager. No post-deploy verification, no error budget awareness, no rollback trigger. It does not test the Osaka failover, the sub four hour target, the DNS redirect or the daily encrypted backups, and the restored copy in a migration receipt is one the team made, not the DR replica.
- It replaces no human review, no standup, no decision and no person. The two-reviewer plus Tech Lead rule stays entirely Bitbucket's. review-route prints at most two suggested specialist roles from the diff, adds nobody to a pull request, and does not know who is awake. sbe status --team shows only changes somebody recorded and is blind to the rest, so it is a view of the process, not of the work. The specialist reviewers and the evidence auditor produce model-written prose that persuades a human and computes nothing.
- The spine, design before verification and install the check before writing the work, is a stated discipline that no tool computes and that Jenkins cannot enforce across days. A complete dossier written after the code passes every gate identically. If the team stops writing dossiers, every verdict degrades to NO-DATA, which does not block, and the whole apparatus becomes files nobody maintains.
- The cost is real and lands on named people who are already the bottleneck. A T3 change owes seven hand-written artifacts from two BAs. The Jenkinsfile, the Helm charts and the Bitbucket configuration are a second hat worn by the Full Stack lead and the Integration Manager, both in Japan, maintaining a pipeline that runs code written offshore overnight. The CONTENT group needs a PIM schema owner who does not exist today, and a four-minute Pimcore rename becomes an export, a branch, an intake, a dossier and a wait for a second human. The first month costs time before it saves any.
- Every threshold shipped was measured on ONE estate, never this one, never a .NET microservice estate, never a Pimcore or Strapi installation, and never a two-timezone team with a night shift. The handover, evidence, impact and converge surfaces are marked INTERNAL-EVAL in the project's own documentation: they ran against its own fixtures and its own diff. Adopting here makes this team the second data point, which is exactly why the advisory phase is not optional.
