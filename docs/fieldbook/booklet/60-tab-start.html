Tab five

Start small

You are not buying a process. You are testing one claim, on one change, this week: that your senior people can stop being the standing verification layer for everything the machine writes. Here is the smallest honest way to find out, what it costs, how to tell it is working, how to tell it is not, and how to take it back out.

Nothing in the first fortnight changes how anything merges. It is files in your own repository, read by people who already work there. The first thing that could stop a merge arrives in week eight, and it is your own platform that does the stopping.

What should we point it at first?

Pick the change you are already dreading. Not a toy, and not the riskiest thing in the backlog either: the ordinary change that you know, from experience, is going to cost somebody senior an afternoon of checking. Six seats, six versions of that same instruction.

Seat one

The staff engineer: the change you already know will land on your desk

Take the next change you are certain you will be asked to review, and run the intake with its author in the room before they write anything. You are not reviewing earlier. You are moving the argument you were going to have in a pull request to the hour where it is cheap, and putting it in a file that the next person can read. When the diff arrives, the reviewer routing picks specialists from the diff itself rather than from whoever is free, and every routed reviewer is read-only by construction.

Seat two

The backend engineer: the contract change whose consumers nobody has enumerated

Be clear about what this does and does not do. It does not go and find your consumers, and it does not stop the change. What it does is make the change harder to treat as a small one: the tier is computed from five answers rather than chosen, and reading the diff afterwards proposes a floor. That floor is a proposal. The tool moves nobody's declared tier in either direction, so a tier declared below the floor comes back as a disagreement somebody has to record by name, against a named commit. The list of who breaks is written by a human, before the change, into the process and data-model artifacts, and the reviewer who reads it can name what is missing. The improvement is that the list exists and is dated, not that a machine produced it.

Seat three

The data engineer: the number Finance already questioned once

Take the figure somebody has already challenged and that survived the challenge because you re-ran the model and got the same answer. Register it: a second derivation whose text genuinely differs from the first, re-run to zero drift against a pinned snapshot. Know the height of the floor before you stand on it. The gate checks that the two derivations differ by more than case, whitespace and comments, and that the two figures recorded from the re-run agree. It executes no query and cannot read which tables each derivation touches, so two reads of the same broken view still agree and still pass. It is a floor worth having and a ceiling worth printing on the wall.

Seat four

The QA engineer: the release where the suite is green and you still do not trust it

Wrap one real suite in the evidence runner, so the claim that it ran carries a receipt naming the command, its exit code, its duration and the paths it covered, minted by the runner rather than typed by anybody. Then look at what the receipt says about the runs you were previously calling green. A check that took no time did not run. A registered check that produced nothing comes back NO-DATA, and NO-DATA is never a pass.

Seat five

The technical business analyst: the requirement that has changed meaning three times

Write the decision record for it: the criteria, two genuinely distinct rejected alternatives, and the condition that would flip the decision back. The check reads the shape, never the judgement. It refuses a file still carrying the shipped template and refuses a record with no flip condition, and a thin but complete answer passes. The value this week is the argument the flip condition forces, and the fact that in three months the argument is still on disk rather than in somebody's memory of a call.

Seat six

The platform engineer: the migration whose rollback has never actually been run

Rehearse it forward and backward against a restored copy, and record the row counts on both sides. The gate reads that receipt; it does not produce it, and nothing resolves the rehearsal id against your job system, so that field is a pointer for a human to follow. A receipt with no row counts is NO-DATA rather than a pass, which is the entire point: the gate says what it compared instead of asserting a comparison it never made.

Every mechanism named above ships with tests and runs in this project's own CI. What none of them do: read your purpose or process artifacts for content, detect that a change needed an approval nobody declared, enumerate consumers, or block anything on their own.

What do the first fifteen minutes actually cost?

Two commands to install, one command to score a change, one recommended action to act on. Nothing else is required, and nothing in your merge path changes.

claude plugin marketplace add khalilmaaouni/BrotherSBE
claude plugin install brothersbe@brothersbe

Then, inside Claude Code, one command that looks at where you are and takes it from there.

/brothersbe:start

The one thing worth doing by hand on the first day, because it is the measurement the rest of the decision rests on, is scoring a real change.

mkdir -p design/my-change     <- the intake refuses a missing dir
sbe intake design/my-change   <- five questions, one JSON file

Five questions: does it change a contract others depend on, does it cross a boundary, is it reversible in under an hour, does it touch money or partner data or personal data or production state, and how many downstream consumers break if it is wrong. Highest matching rule wins. Then ask for exactly one next step rather than a menu.

/brothersbe:next

What you have deliberately not done yet

No pipeline stage, no merge check, no branch protection, no keys, no registry. Nobody's merge is slower and nobody's build is redder. Everything above is a verdict printed on a laptop and a few files on a branch, which is exactly why it is safe to try on a real change instead of a sandbox.

How do we roll this out without stopping anyone's merge?

Advisory first, every time. Print verdicts for weeks before anything is allowed to block, and read them against your own codebase's idioms rather than against a vendor's assumptions. The order below works on a plain repository with nothing special enabled.

The stronger path, where your plan includes it

Some code hosting tiers offer an evaluate-only mode for repository rulesets, which lets a rule report what it would have done across many repositories at once without refusing anything. Where a team has that tier, use it: it is a better advisory phase than a wrapped pipeline stage, because it measures the rule itself rather than one job's exit code. Do not plan around it before you have checked. That mode is gated at organisation and enterprise level, so on a plain repository it is simply not there, and the eight-week ladder above assumes it is not.

What happens on the first pull request that runs strict?

The build goes amber before it goes red, because the first strict stage is one stage on one path, and most changes never touch it.

The verdicts arrive blocker first. One of them is a FAIL and everybody looks at it. Three of them say NO-DATA and almost nobody does, which is the reading that matters.

Expect these four, and expect the third to be the one that changes how your team reads a green build.

The one that surprises people in week nine

A receipt is bound to two things on purpose: the head commit it was minted against, and the exact bytes of every file it says it covers. Both have to still hold when somebody checks it. So if your repository rewrites history on merge, a receipt minted on the branch tip stops matching at the merge commit, and any later commit at all moves the head out from under it. That is strict by design, and it means regenerating receipts on the post-merge head belongs in your pipeline as a designed step rather than as something you work out during an incident.

How will we know it is helping, and how will we know it is not?

Decide the readings before you start, so the answer in six weeks is a number somebody wrote down rather than an impression somebody defends. Two of these readings are designed to tell you to stop.

ReadingHealthyWhat an unhealthy reading is telling you
The tier mix over four weeksA spread, with the cheapest tier the largest group.If nearly everything comes back T2 or T3, somebody is answering the intake wrongly, or your boundaries genuinely are that wide. Re-score ten changes with two people in the room before you blame the tool or the team.
NO-DATA, per check, per weekFalling, and each remaining one explainable.The same check returning NO-DATA week after week means the evidence is not being produced. That is a workflow problem, not a verdict problem: usually the command never runs where you think it runs, or the receipt is written into the very tree it covers.
Share of the diff nothing could readSmall, and known by name.A large unmeasured share means the automated readers are looking at a corner of your estate. Say that out loud rather than reading a green run as coverage.
Open questions on a handoverTyped, specific, and answered by name.Always empty means the handover has become a formality. That field is written empty by design and only a human fills it, so an empty one is a person deciding not to.

Have the two or three people carrying that load log it for a fortnight before you start and a fortnight after, or you will not be able to answer the only question that matters.

If four weeks in, the only thing that has changed is that people write more files, stop. That is a real result and this page will not argue you out of it.

How do we take it back out?

Plainly, because an adoption you cannot reverse is a decision nobody should make on a Tuesday.

  • In the first three weeks there is nothing to undo. Everything written is files on a branch in your own repository. Delete the branch, or keep the files and stop running the commands.
  • Remove the plugin with claude plugin uninstall brothersbe. That removes the tooling, and it removes nothing you wrote: your dossiers, receipts, pipeline stages and branch settings are yours and you remove those yourself.
  • Go back a version rather than out entirely with scripts/rollback-install.sh, which previews by default and only acts on --apply, and which refuses rather than guesses when it cannot identify the installation it is meant to move.
  • Stop enforcing without removing anything by putting the CI stage back to its wrapped, advisory form. That is a one-line change in your own pipeline file, because the enforcement was always yours.

Which commands will we actually run?

# install, update, remove
claude plugin marketplace add khalilmaaouni/BrotherSBE
claude plugin install brothersbe@brothersbe
claude plugin update brothersbe    <- restart to apply
claude plugin uninstall brothersbe

# inspect before you trust: one session, no persistent install
git clone https://github.com/khalilmaaouni/BrotherSBE \
    ~/.claude/skills/brothersbe
claude plugin validate ~/.claude/skills/brothersbe
claude --plugin-dir ~/.claude/skills/brothersbe

# does the installed copy match the published manifest
sh scripts/verify-install.sh

# is this machine able to run what it is about to promise
sbe doctor

# week one: score a real change, then ask for one next step
mkdir -p design/my-change
sbe intake design/my-change
# then, in Claude Code: /brothersbe:start, /brothersbe:next

# week five onward, in CI, advisory first
sbe impact . --base origin/main    <- advisory: no --strict
sbe verify design/my-change        <- design check plus gates

# the enforcing form, once you have decided to enforce
sbe impact . --base origin/main --strict \
    --intake design/my-change/00-intake.json

Every command above is a surface this project ships. What none of them do is merge, approve, deploy or write to production.

Four things, and a fifth that is not a purchase. None of them ship in the box, and a plan that assumes otherwise fails in week eight rather than week one.
