Tab four

Why trust it

Everything claimed so far is worth exactly what the mechanics underneath it are worth. This part is the mechanics, in the order a sceptical engineer asks for them: what a verdict means, what happens before code, what a receipt is, who is allowed to write, what actually stops a merge, and every place the system will not help you.

What does a green build actually prove?

Most tooling has two answers: it passed, or it failed. That is one answer short, and the missing one is where wrong results live.

A check can pass. A check can fail. And a check can find that there was nothing there to read at all, which is a completely different fact and deserves its own word.

Absent evidence is NO-DATA. NO-DATA is never a pass.

Three of the situations below contain no evidence whatsoever. A two-state system has only one place to put them, and it is the good one.

This is not a convention anybody has to police. A check is refused registration at construction if it declares PASS as its empty state, so the rule cannot be forgotten by a check written next year. A meta-test walks the registries themselves rather than a hand-typed list, so a new check is covered the day it is registered.

The same discovery rule generates the check register printed later in this part, which is why that table and the honesty test can never drift apart: they enumerate the same objects.

The fine print, printed here rather than buried

NO-DATA is never a pass as a verdict, and it is not a block as an exit code. Under --strict, a FAIL exits nonzero and a NO-DATA prints and exits zero. So a change that declares nothing at all can produce several NO-DATA lines and a green build.

That is deliberate, and it is also the sharpest edge in the product. It means a clean run is not a safety claim. It means the question to ask of a green build is not "did anything fail", it is "how many of these lines say NO-DATA, and why". A team that reads a repeated NO-DATA as noise has turned a control into decoration.

Why design before code, rather than better review?

The decisions that cost the most are taken before there is a diff to review. The grain of a table. The contract two other teams already depend on. Which of five stores is the system of record. By the time a reviewer opens a pull request, all of those are settled, and the review is an argument about spelling.

So the order is fixed. A change is scored first, by five objective questions with a first-match-wins ladder, and the tier decides how much writing it owes. Most changes come out at the bottom tier and owe nothing at all, which is the only reason the top tier can afford to owe a great deal.

What the design checks then read is shape, never content, and this is where the mechanism stops and your judgment starts. The data-model check fails an entity with no named system of record and a relationship with no stated cardinality. The decision record must carry two distinct rejected alternatives and a condition that would flip it. A diagram node that traces back to no declared entity fails. A file still carrying the shipped template fails. That is the shape of it, and shape is all of it.

None of it can tell a correct answer from a confident wrong one. Naming the wrong system of record passes every check that ships. A one-sentence purpose brief passes. A complete dossier written after the code passes identically to one written before it.

The value is the argument the data model forces out of a room. The file is only the receipt for having had it.

Why a receipt beats a green stage

A green stage is a name and a conclusion. Nothing in it records what ran, how long it took, or which files it was looking at. That is why a skipped job and a four-minute job look the same from the merge rule's side of the wall.

A receipt is minted by the runner that executed the command, never typed by the thing making the claim. It seals the command with its arguments redacted, the exit code, the duration, the base and head commit, and a content digest of every path the check declared it covers.

What a receipt lets you askWhat a green stage can answer
Which exact command produced this?Nothing. A name is not a command.
Did it take any time at all?Nothing. A zero-second success is still a success.
Which commit was it looking at?The head of a branch that has since moved.
Have the files it covered changed since?Nothing. Digests were never taken.
Was there a receipt at all?Nothing, and the absence looks like success.

That last row is the ran gate, and it is the smallest idea in the product: a check that exited zero having taken no time did not run. Registration matters for the same reason. A check has an entry naming the command it binds, so a receipt points at something declared in advance, and editing that entry invalidates every receipt minted before the edit.

Now the ceiling, because a receipt proves less than the word suggests. The highest trust level a continuous integration run reaches is CI-claimed, which the module's own text defines as CI-shaped metadata that nothing verified. A laptop exporting the same run identifier on a clean tree earns the same label. The seal is a checksum, not a signature, and there is no protected evidence level in this release. Receipts are also strictly commit-bound: one minted before a rebase fails at the merge commit, and a covered file rewritten afterwards invalidates it even when the bytes are identical, which is why a receipt is written outside the tree it covers and regenerated by the pipeline on the final head.

The trust level is printed on every receipt rather than left to be inferred, and a run carrying no pipeline run identifier is labelled local-advisory. What the label records is what the environment claimed, not where the run happened, which is exactly why the level above it is called CI-claimed rather than CI-verified.

Seven roles read. One role writes. The one that writes takes a single briefed task with a declared scope, and holds no merge, rebase, push or deploy rights of its own.

Now the part the tools column does not say out loud. Read-only here means no Edit tool and no Write tool. Every reviewer still holds a shell, and a shell can write a file. That last step is held by a written rule inside the role's own definition rather than by the tool list, so the half of this separation you can audit by reading a table is the half in the table, and the remainder is a written rule with all the strength a written rule has.

Two more limits belong beside that, because the separation is stronger than the fence around it. The scope comparison that keeps a worker inside its declared files runs as an editor hook whose own rule is to fail open, loudly: it binds work done through that editor, and it binds nobody typing in a different one. And the task registry refuses a taken branch, a taken worktree and a re-opened task identifier, but it never compares file scopes between two different tasks, so two people holding the same file get a registry a human reads, not a refusal.

What actually stops a merge

Four failure classes get a hard gate, chosen because each of them fails quietly rather than loudly.

GateWhat it readsWhen its evidence is absent
numbersA manifest with a pinned snapshot, a second derivation whose text genuinely differs, and two figures that match.NO-DATA
migrationA rehearsal receipt recording the forward leg and the reverse leg, both run, with row counts on each side.NO-DATA
approvalA host-verified signature carrying an approval trailer that names somebody other than the author and the committer.NO-DATA when the change declares nothing at all, and FAIL when it declares an approval and carries no identity behind it.
ranA receipt showing a registered command that exited zero and took a nonzero amount of time.NO-DATA

Read the last column as the design decision it is. The default is NO-DATA, because absence genuinely might mean "there was no migration in this change". The approval gate is the one place a broken claim is told apart from an absent one: declaring an approval and putting no identity behind it is a claim that failed, so it reads FAIL, while a change that declared nothing reads NO-DATA like everything else. Self-approval fails at both ends.

Two things follow from that, and both of them cut against the product. A change that quietly needed an approval and never declared one is a green build, because there was nothing to read. And the approval gate is only ever real where the reviewers' public keys are imported on the machine running it: an agent without them reports an unverifiable signature, so every approval on that host reads NO-DATA no matter how carefully it was signed. On a fresh pipeline that is the normal state until somebody does the keyring work.

Severity is a separate axis from the verdict, and it changes the exit code and nothing else. It never changes what a check examines.

StampWhat it means here
gateA FAIL exits nonzero under --strict. This is the only severity a merge rule can be bound to at all.
softA FAIL is graded and exits nonzero only under the opt-in --strict-soft.
NO-DATAThe empty state. Reported by name, never decides an exit code in either direction.
FAILThe empty state for a check where something was declared and nothing stands behind it, which is a broken claim rather than an absence.

Now the sentence that most tools in this category avoid. Nothing here stops a merge on its own. Every gate is a command that prints a verdict and, under --strict, exits nonzero. Three separate pieces of your own wiring sit between that nonzero exit and a merge that will not go through.

Two things about your host that are easy to get wrong

A file naming code owners does not block anything by itself. It nominates reviewers. Something behind it, branch protection or a branch ruleset, has to require their review before the nomination has teeth. A repository with the file and neither of those has a suggestion, not a control.

Advisory first, enforcing later is the right rollout, and it is not universally available. On the host that offers branch rulesets, the advisory evaluate mode is gated at organisation and enterprise level, so a smaller plan gets on or off rather than a soft first fortnight. If you are on one of those plans, get the same effect by wrapping the job in your own pipeline's soft-failure mechanism for the first two weeks, then unwrap one stage at a time.

What it will not tell you

The honest half of the product, collected in one place so that it is not the hardest part to find. The body of each limit lives in the limits file, so there is one copy of the wording and this page cannot quietly soften it.

The four that matter most to a small team

Nothing detects that a change needed an approval. The gate verifies an approval that was declared. What you actually need behind it is a code owners file and branch protection on your own repository.

Two derivations differing in text is a floor, not a proof of independence. The numbers gate proves the two texts differ beyond case, whitespace, comments and trailing punctuation, and that two transcribed figures match. It executes no query. Two reads of the same broken view agree perfectly and both pass.

A rehearsal identifier is a pointer, not a resolution. Nothing calls your job system to confirm that the rehearsal happened, or that the receipt describes the run it names.

This repository's own merged pull requests carry no independent review. Applied to its own history, the approval law reports NO-DATA, not PASS. That is the honest answer to whether the project practises what it sells on that one axis: not yet, and it says so here rather than waiting to be asked.

What stays human, and what you have to supply

Three things are worth being blunt about before anybody signs anything.

It never gets apply rights of its own. Nothing in it merges, approves, deploys or publishes, no role it ships is given a merge, push or deploy right, and it never learns that a human did any of those things. It drafts the command and its rollback, and a human runs it. Be equally clear about what that is not: it is not a fence between an agent and your production. Every role it ships holds a shell, so the thing that actually stops a deploy is the credentials on the machine and the rights on your host, and those stay your job. A manual approval step in your pipeline and a signed approval trailer are also two different approvals, and treating them as one is the most dangerous sentence available in this area.

It stops at the deploy. No monitoring, no alerting, no error budget, no rollback trigger. No receipt describes production state, so the question your support team actually asks, is it live and is it fixed, has no answer here.

It sees only what passes through a diff, a JSON file or a markdown file. A field retyped and saved in an administration console, a campaign built in a marketing tool, a voucher rule, a content type published from a headless store: none of those produce a diff, so none of them gets a design phase, a gate, a linter or a receipt, and nothing notices the omission. On the one estate this was mapped against, a large share of what the commercial and support side logged as a bug turned out to be product data or content rather than code. That is one team's experience rather than a measured rule, and the useful move is to check the same thing on your own tickets before assuming the gap is small. Say it on day one either way, not after the first miss.

What the team supplies is the other half of the system, and it is not a short list: the pipeline job, the merge rule, the branch protection, the signing keys on the machine that verifies approvals, the entry describing each registered check, and the export that makes a schema visible to git in the first place when it lives in a tool rather than in a file.

And then the judgment, which no part of this touches. Whether the system of record you named is the right one. Whether the alternative you rejected was the one worth rejecting. Whether the second derivation is genuinely independent or merely differently worded. Whether the check somebody registered is a good check. The product's position is that it makes those questions visible, arguable and dated, and answers none of them.

A four-week adoption that does not get switched off

One repository. One lane of work. Advisory first, then enforcing, one stage at a time. Do not roll this across an estate before one team has an opinion, because a control that arrives everywhere at once gets switched off everywhere at once the first time it is inconvenient.

Week 3Unwrap one stage. Bind the merge rule to it. Leave the rest advisory.One uncomfortable pull request. That is the system working, and it is the only week that proves the wiring is real.

That second sentence in week two is the entire control, and it is a human agreement rather than a mechanism. What the mechanism contributes is that everything capable of weakening a gate is a file: the --strict flag lives in your pipeline configuration, and a waiver is an exemption file naming which gate it waives and why. Both of those arrive as a diff somebody can see, which is a real improvement on a sentence typed in a session that leaves no trace. It is not a lock. The exemption check reads that a reason is present, never whether the reason is a true one.

Try it on the change you would be most embarrassed to get wrong.
