# BrotherSBE for Dummies, the persona parts

Founder direction 2026-08-01, verbatim intent: the explainer stays the quick summary; the real depth lives in the book, persona by persona, from dummies to definitive experts, with real work, real collaboration practice, the Obsidian vault used for real, and enough process diagrams and hard detail that a very technical reader stops suspecting a gimmick.

The existing thirteen chapters (00 to 12) are Part One and Part Two: what it is, install, the loop, evidence, gates, vault basics, coordination basics, cookbook. This spec adds six chapters, 13 to 18: Part Three, one deep dive per persona, and Part Four, team practice and mastery. The two full domain volumes approved on 2026-07-30 (data engineering on Snowflake and Databricks, infrastructure on AWS, Azure, Kubernetes) remain future separate volumes; chapters 14 and 15 borrow their approach at chapter scale and say so.

## Laws binding every chapter (the builder and replay enforce most of them)

1. Replay law: a fenced bash block followed immediately by a bare fenced block is EXECUTED by evals/replay_book.py and the output is byte-compared. Only write such a pair for commands you actually ran while writing, from the exact working directory the chapter states. Anything you cannot run on this machine (warehouse SQL, cloud CLIs) goes in a text-tagged fence with the line "NOT EXECUTED HERE:" immediately above it, exactly that phrase.
2. Never run commands in the repository root: copy the estate first (cp -r docs/book/estate /tmp/sbe-book-chNN) and work there, the way chapters 05 to 09 do. A bare gate or explain run at the root writes decision packages into .sbe/ and breaks the install verifier.
3. Mermaid diagrams live in mermaid-tagged fences; the builder renders them offline and replay ignores them. Each persona chapter carries at least three: a process or swimlane view, a data or lineage view, and one more the story needs.
4. Register: the "for Dummies" voice: second person, warm, direct, every term spelled out on first use, short paragraphs, verdict sentences. Expert depth goes in blockquotes opening with "Expert note:" so a beginner can skip them and an expert can skim for them. Zero em or en dashes. No private or client names. No hype vocabulary.
5. Honesty: a command that refuses is shown refusing and the refusal is taught (policy and exceptions refuse today by design; that is a lesson, not a bug to hide). Nothing is claimed that a shown command did not prove. Forward-looking features carry "ships in a later loop" beside them.
6. Word targets: chapters 13 and 14 between 3000 and 4000 words; 15, 16, 17 between 2500 and 3500; 18 between 2000 and 3000. Depth over padding: cut before you pad.
7. Python 3.9 stdlib only for anything executed. Chapters may declare machine requirements the way existing chapters do only if genuinely needed; prefer stdlib-only so every machine replays everything.

## Chapter 16: Working as one team

The practicum behind chapter 11. A three-person team plus Claude sessions ships a quarter of changes without trampling each other. Teach with concrete scenes: the morning ritual (read the failures index before touching the area); claiming work so only one writer edits a file at a time, shown with the real task registry commands on a /tmp copy; what happens when two people need the same file the same afternoon (queue, never parallel, and why); the review wave: the seven read-only reviewer agents by name, what each hunts, how a refute verdict reads, why reviewers never write; the learning law: a lesson becomes team law only through a reviewed pull request into the learned file, nothing changes behavior silently; the handoff: what a complete handoff names (done with evidence, in flight with exact stopping point, not started, open questions). Retell the shared-staging-area incident generically as the war story that produced the stage-by-name rule. Diagrams: the team loop swimlane, the review wave fan-out, the lesson-to-law path. Expert notes: running multiple Claude sessions against one tree, why worktrees exist, what the fence registry looks like at 2am when something died.

## Chapter 17: The vault in Obsidian, for real

The persona keeps a project alive across months. Open the shipped memory template in Obsidian and walk it: the real tree (ls output of memory-template, executed), what each folder is FOR with one concrete example each: overview as the page a newcomer reads first, open items as the only to-do list that survives a restart, the failures index as the pre-work ritual that prevents repeat mistakes, session logs as the handover that lets a stranger continue tomorrow, the learned file as team law. Linking: double-bracket links, what the graph view actually buys (finding the failure note you forgot exists), naming discipline. The automatic layer: which files the machine writes (telemetry, version marks), shown with a real run against a throwaway vault in /tmp via the environment override, and the privacy defaults (transcript capture off, what opt-in changes). What NOT to store: secrets never, code that lives in git never, one fact one home. A day in the vault: morning read, milestone checkpoint, session close, and what compounds after a month. Diagrams: vault structure map, the write-and-read loop across sessions. Expert notes: multi-project vaults, pointing the vault variable at a shared drive, when to split a vault.

## Chapter 18: From dummy to definitive expert

The ladder, per persona. For each of the four personas (beginner builder, backend engineer, data engineer, platform or team lead): what level one looks like (follows the guided commands, reads NO-DATA as "not checked yet"), what competent looks like (writes the intake honestly, reads receipts before believing green, argues tiers up not down), what expert looks like (designs the checks before the work, teaches the refusals, extends decision tables, reviews other people's evidence). The anti-pattern gallery, each with its tell and its fix: green without a receipt, tier shopping, prose as a control, the hand-typed receipt, the deleted failing test, the silent fallback. Self-tests: for every law you rely on, can you name the thing that enforces it and make it fire on purpose. Close the book with the one-sentence law: absent evidence is NO-DATA, and NO-DATA is never a pass.
