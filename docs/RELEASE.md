# Releases: how a version is cut, and how you pin one

This runbook exists because the laws change under their users. An install whose
only name is a commit hash cannot be talked about, compared, or pinned by a
human, and a security page that says "verify what you installed" without a
manifest to verify against is an invitation, not a control. This page is the
procedure; what it does NOT do is execute itself: every step below is run by a
human, and the two that publish are gated on one.

## The version scheme

Semantic versions in the `VERSION` file, one line, starting at `1.0.0-rc.1`.

- MAJOR: a law or a gate changes meaning, so a green run before and after does
  not attest the same thing.
- MINOR: a new check, law, or tool; existing verdicts keep their meaning.
- PATCH: fixes and copy that change no verdict.
- `-rc.N`: a candidate; the promises in `INVARIANTS.md` hold, the tag may still
  move before the final version. A version with no suffix is a cut release.

`DIGEST.md` names the version in its header, so an injected law block says
which version it came from; `tools/test_sbe.py` asserts the header matches
`VERSION` so the two cannot drift.

## Pinning an install to a release

```bash
git clone --branch v1.0.0-rc.1 --depth 1 <repository-url> ~/.claude/skills/brothersbe
```

Then verify the bytes you got against the manifest that release ships:

```bash
cd ~/.claude/skills/brothersbe && scripts/verify-install.sh
```

PASSED means your files match the manifest in both directions (nothing
missing, nothing altered, nothing extra). It does not prove the manifest is
authentic: take the manifest from the tag you trust, not from the same
untrusted channel as the code. If you do not pin to a tag, pin to a commit and
record the hash, as [SECURITY.md](../SECURITY.md) documents.

## Cutting a release (maintainer)

In this order, the first four in ONE commit, so no version of the tree ships a
manifest that disagrees with its own files:

1. Bump `VERSION` and the version named in the `DIGEST.md` header.
2. Write the `CHANGELOG.md` entry: newest first, each line naming the behavior
   that changed and the check or test that proves it.
3. Regenerate the manifest: `scripts/checksums.sh CHECKSUMS.sha256`.
4. Run the gates (`evals/run_evals.py`, `evals/test_no_data_class.py`,
   `tools/test_sbe.py`) and commit the four files together only when green.
5. Tag: `git tag -a v<version> -m "<one line from the changelog>"`. Human-gated.
6. Push the tag. Human-gated, and on this machine it goes through the
   operator's own push process, never a bare push from a session.

## What has actually been executed

Honesty over ceremony: steps 1 to 4 have been executed for `1.0.0-rc.1` (the
manifest in this tree was generated by the script beside it, in the same
commit as the version). Steps 5 and 6 have NEVER been executed as of
2026-07-27: no tag exists yet, so the pin command above is the documented
intent, verified against git's own syntax but not against a published tag of
this repository. This paragraph is updated when that changes, because a
runbook that presents untested steps as proven is the defect class this whole
project exists to catch.
