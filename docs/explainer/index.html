The basics

What it is

BrotherSBE runs inside Claude Code, the terminal based coding assistant that Anthropic makes. You do not learn a new tool or a new syntax. You describe the outcome you want, in ordinary language, the way you would explain it to a colleague sitting next to you.

From there, BrotherSBE sizes the risk of the change, asks for design work in proportion to that risk (a one line fix gets none, a change to something central gets a real plan first), and proves the result with checks that actually ran on your machine, not ones it remembers running from before. Where it could not check something, it says NO-DATA, meaning no evidence either way, instead of quietly assuming the best.

Ninety seconds

The story in ninety seconds

The book's running example is small on purpose: "a tiny nightly pipeline plus a read API, real enough to run and small enough to hold in one look" (from docs/book/estate/README.md). Run python3 pipeline.py --date 2026-07-01 and it prints three lines. The last one says wrote 3 rows to daily_totals.

Open the file it just wrote and count what is actually there. Two rows: one for EU, one for US. Not three.

Nobody built the pipeline to lie. The printed line and the file on disk come from the same run, seconds apart, and they still disagree. That gap is the whole reason BrotherSBE exists: absent evidence is NO-DATA, and NO-DATA is never PASS.

Nine chapters later, the fix is one changed line in pipeline.py, landed only after a new test watched the old code fail first, then watched the fix pass. Section 5 below (the whole journey) walks that same fix stop by stop, with the real commands and the real output. Tutorial 1 (below) lets you run every step of it yourself.

Getting it running

Install in two commands

claude plugin marketplace add khalilmaaouni/BrotherSBE
claude plugin install brothersbe@brothersbe

Verified working on 2026-08-01. To update later, run claude plugin update brothersbe.

Prefer to look before you trust? Clone the repository and run claude plugin validate BrotherSBE first.

Keeping it fresh

Two commands cover it, and they do two different things. claude plugin update brothersbe pulls the newest release of the plugin itself; restart Claude Code for it to apply. claude plugin marketplace update brothersbe refreshes where that release comes from, which is a separate step from updating the plugin.

You should not have to remember to check by hand. BrotherSBE announces at the start of a session when the installed version has changed since the last one you ran, so a stale install gets named out loud instead of silently carried forward.

A submission packet for the community plugin marketplace is prepared but not yet sent; the official directory itself is curated by Anthropic with no application process. The two commands above are the real install path today, not a placeholder for one still to come.

Your first move

Your first project

Open Claude Code in any project and type:

/brothersbe:start

That one command is the only one you truly need. It is part of a guided set of four:

/brothersbe:start

Begin or resume. It finds where you are, so you never have to hunt for it yourself.

/brothersbe:next

Exactly one recommended action, and why it is the right one right now.

/brothersbe:status

Where things stand, in plain words, with nothing left to decode.

/brothersbe:help

The whole map, for when you want to see everything at once.

You never have to memorize the machinery. Just take one action at a time.

End to end

The whole journey, end to end

Every change, big or small, passes through the same six stops. What follows is the estate fix from the story above, walked through stop by stop, each one with the real command and a real, labeled excerpt of what it printed.

1. Describe and size

Real run, from docs/book/05-the-first-loop.md.

printf 'y\nn\ny\nn\nsome\n' | bin/sbe intake /tmp/sbe-book-ch05-dossier
tier T2 (artifacts required: 01, 02, 03, 05, 06, 07) written to /tmp/sbe-book-ch05-dossier/00-intake.json

What to notice: five yes, no, and count answers become one tier, mechanically. A decision table, not a judgment call.

2. Design in proportion

Real run, from docs/book/05-the-first-loop.md and docs/book/09-loops-that-converge.md.

bin/sbe design /tmp/sbe-book-ch05-dossier --strict
artifacts  FAIL     tier T2 requires 01, 02, 03, 05, 06, 07; missing: 01-purpose.md, 02-process.md, 03-adr.md, 05-data-model.md, 06-diagrams.md, 07-verification.md; examined . under /tmp/sbe-book-ch05-dossier [severity: gate]

Contrast: a T1 dossier that owes one file and has it.

artifacts  PASS     tier T1: every required artifact present, carrying content, and naming subject matter the rest of this dossier also names; except 01-purpose.md, which this dossier has nothing else to be coherent with, so that was not checked; examined . under /tmp/sbe-book-ch09-dossier [severity: gate]

What to notice: the same command FAILs a T2 dossier that owes six files and has none of them, and PASSes a T1 dossier that owes one and has it. The tier decides how much design is owed; nobody negotiates it by hand.

3. Plan and build

Real run, from docs/book/07-the-task-registry.md.

python3 "$ROOT/bin/sbe" task open --id fix-totals --agent engineer-a --role writer --base "$BASE" --verify "python3 pipeline.py --date 2026-07-01" --owns pipeline.py --cwd .
sbe task open: fix-totals is open. engineer-a (writer) owns 1 path(s): pipeline.py. Base 0b137953313d. Close runs the diff postcondition against exactly this declaration.
python3 "$ROOT/bin/sbe" task close fix-totals --cwd .
sbe task close fix-totals: PASS. 1 changed path(s), all inside the declaration. Closed clean.

What to notice: the close is a diff check against the declaration, not a claim. Two layers exist today: sbe task open and sbe task close (shown above, from the book) fence a writer to declared paths, and sbe work start and sbe work finish sit on top for a whole plan task, giving it its own branch and separate draft workspace and refusing to finish without a receipt bound to the exact commit. The book predates the work pair, which is why this real excerpt shows the task layer.

4. Prove

Real run, from docs/book/06-evidence-not-vibes.md and docs/book/08-gates-and-decisions.md.

bin/sbe evidence run --out /tmp/sbe-book-ch06/test-receipt.json --covers pipeline.py --covers test_estate.py --cwd docs/book/estate -- python3 test_estate.py
sbe evidence run: receipt written to /tmp/sbe-book-ch06/test-receipt.json. Trust LOCAL-ADVISORY (no SBE_CI_RUN_ID was set when this ran, so nothing outside the machine that wrote it attests to it). Command exited 0 in <N.NNNs>, over 2 covered file(s) from explicit --covers. stdout and stderr are recorded as digests only. argv held 0 secret-shaped token(s) and was recorded verbatim.
python3 "$ROOT/bin/sbe" gate approval .
approval  FAIL     APPROVAL (of 1 APPROVAL file(s) read) declares 'Approved by Dana Reviewer', but approval is a typed name with no signature or review id; a name in a text field is not a control (add a signed Approved-by trailer or a Reviewed-in review id) [severity: gate]

What to notice: the receipt only proves a command ran. The gate separately proves a second human looked, and a typed name in a file is refused by name, every time.

5. Review and converge

Real run, from docs/book/09-loops-that-converge.md.

python3 test_estate.py TestEstate.test_the_wrote_line_matches_the_rows_actually_on_disk
test_the_wrote_line_matches_the_rows_actually_on_disk (__main__.TestEstate) ... FAIL
AssertionError: 3 != 2 : the pipeline claimed 3 row(s) but wrote 2

What to notice: this failure is the loop converging correctly. A test that has never been watched failing is a test nobody has proven tests anything. The book's own stopping rule: once the same refusal repeats twice for the same reason, stop building and go back to probe. A third identical try will not do what the first two could not.

6. Human merge

Real run, from docs/book/11-coordinating-humans-and-agents.md.

python3 "$ROOT/bin/sbe" task close review-the-bundle --cwd . --force --who reviewer-1 --why "agent-1 receipt verified, row-count message still off by one, tracked by hand until sbe note ships"
sbe task close review-the-bundle: FORCED by reviewer-1 (agent-1 receipt verified, row-count message still off by one, tracked by hand until sbe note ships). The record carries the disposition and the violation list; this close is never read as clean.

What to notice: a human decision that overrides the fence is recorded as FORCED, never PASS, forever. The tool never fabricates consent. Honestly: sbe pr verify <number> --repo owner/name is the real command for live GitHub pull request evidence, but no chapter in the book runs it against a live pull request with captured output, so this stop shows the reviewer's actual bundle workflow rather than an invented one.

Practical advice

Riding the loops

A few habits make the difference between fighting BrotherSBE and working with it.

  • Start or adopt. Use /brothersbe:start on a project with no BrotherSBE history yet. Use /brothersbe:adopt when the project already has code and habits that BrotherSBE did not set.
  • Tiers only move up. A tier is computed from a small set of answers, not chosen. You can argue for a higher tier than the one it computed; you cannot argue your way to a lower one.
  • Two failed tries, then stop. A verify that comes back with the same refusal twice in a row, for the same reason, means stop building and go back to design. A third identical attempt fixes nothing the first two did not already rule out.
  • NO-DATA is not a verdict. It means no evidence either way. It is never quietly treated as a pass, and it is never quietly treated as a block either: it gets named, out loud, every time.
  • Receipts come from running commands. A result is recorded because it actually ran on a machine, never because someone typed what they expected it to say.
  • One writer per file, at a time. A fence declares which paths a task owns while it is open, so two workers never edit the same file underneath each other.

An honest range

Really good at, honestly not good at

Really good at

  • Backend and data system design, worked out before code gets written.
  • Schema migrations with a rollback rehearsed and checked before the real run.
  • Evidence backed review of changes and pull requests.
  • Catching errors a program silently swallowed instead of surfacing.
  • Keeping a team honest about what was actually checked.

Honestly not good at

  • User interface and visual design work.
  • Tiny throwaway scripts, where the ceremony would outweigh the change. T0 exists for exactly this: near zero ceremony.
  • Hosts other than Claude Code, today.
  • Replacing your judgment about what is worth building.
  • Working without a git repository.

Where it fits

Use cases

Add an API endpoint safely

A new endpoint touches a contract other code will depend on, so it earns a real tier before any code gets written. Start with the guided command; it asks the questions that decide how much design the change actually needs.

/brothersbe:start

Change a schema with a rollback you rehearsed

A schema change is exactly the kind of move that raises a tier on its own, whatever a first guess claimed. sbe impact reads the real diff and says plainly when the declared tier disagrees with what the change actually touches.

bin/sbe impact . --base <commit> --intake <dossier>/00-intake.json

Investigate a number nobody trusts

Most disputed numbers come down to a claim nobody checked, the same gap the estate pipeline shows in the story above. sbe evidence verify reads a receipt and says plainly whether the working tree behind it was ever in a state anyone else could reproduce.

bin/sbe evidence verify <receipt>.json --cwd .

Review a pull request before release

A review that only reads the diff is a review that trusts the author's memory of what ran. sbe pr verify is built to check a live pull request's evidence instead of taking the description's word for it.

sbe pr verify <number> --repo owner/name

Adopt a legacy repository

A repository with years of history and no BrotherSBE habits needs a different first step than a blank one. /brothersbe:adopt reads what is already there before proposing anything, instead of assuming a clean slate.

/brothersbe:adopt

Keep a team's status honest

A status update drifts from what actually happened the moment someone summarizes it from memory. /brothersbe:status reads the real state, the open fences, and the open decisions, and says so in plain words.

/brothersbe:status

Three tutorials

All three run inside a clone of this repository, against the same worked estate example from the story above. Every command below is real; run it and expect output shaped like what is shown.

1. Your first verified change

T0 to T1 on the estate pipeline. Source: docs/book/09-loops-that-converge.md.

  1. Intake at T1:

    printf 'n\nn\ny\nn\nsome\n' | bin/sbe intake /tmp/sbe-book-ch09-dossier
    tier T1 (artifacts required: 01) written to /tmp/sbe-book-ch09-dossier/00-intake.json

  2. Write 01-purpose.md, then check the dossier:

    bin/sbe design /tmp/sbe-book-ch09-dossier --strict
    artifacts  PASS     tier T1: every required artifact present, carrying content, and naming subject matter the rest of this dossier also names

  3. Add the new test, and run it against the old code first, to prove it can fail:

    python3 test_estate.py TestEstate.test_the_wrote_line_matches_the_rows_actually_on_disk
    AssertionError: 3 != 2 : the pipeline claimed 3 row(s) but wrote 2

  4. Apply the fix in pipeline.py, changing "wrote %d rows to daily_totals\n" % (len(rows) + 1) to % len(rows), then run the pipeline:

    python3 pipeline.py --date 2026-07-01
    read 3 orders from orders.csv
aggregated 2 region(s) for 2026-07-01
wrote 2 rows to daily_totals

  5. Run the full suite:

    python3 test_estate.py
    test_the_wrote_line_matches_the_rows_actually_on_disk (__main__.TestEstate) ... ok
Ran 5 tests in <N.NNNs>

OK

  6. Fence and land: open the task, run evidence, close clean, then commit.

    python3 "$ROOT/bin/sbe" task close fix-row-count-message --cwd .
    sbe task close fix-row-count-message: PASS. 2 changed path(s), all inside the declaration. Closed clean.

2. A risky migration done honestly

Tier rises, gates demand rehearsal evidence. Source: docs/book/12-cookbook.md.

  1. Declare T1 first, on a change that is actually bigger. The real diff disagrees:

    python3 "$ROOT/bin/sbe" impact . --base "$BASE" --intake /tmp/sbe-book-ch12-schema-dossier/00-intake.json
    proposed tier T3 (a floor, not a ceiling), declared tier T1
verdict: REVIEW-REQUIRED

  2. Re-answer honestly. The tier rises to T3, and a re-run of sbe impact now agrees:

    proposed tier T3 (a floor, not a ceiling), declared tier T3
verdict: PASS

  3. Before the real migration runs, write a rehearsal receipt:

    python3 "$ROOT/bin/sbe" evidence run --out /tmp/sbe-book-ch12-receipts/rehearsal-receipt.json --covers backfill_partner_id.py --cwd . -- python3 backfill_partner_id.py --rehearse
    REHEARSAL: would add partner_id to 3 row(s), nothing written

  4. Verify the rehearsal receipt before trusting it. A dirty working tree earns NO-DATA, not a pass, even though the rehearsal itself ran cleanly.

  5. Only a clean tree under real continuous integration, with a minted run id, ever clears LOCAL-ADVISORY into the higher trust level. Neither receipt here does that on its own.

3. Reviewing a pull request with evidence

Source: docs/book/11-coordinating-humans-and-agents.md.

  1. A reviewer tries to own the evidence store it is about to review. Refused:

    sbe task open: refused. A reviewer task may not own '.sbe/evidence': it overlaps the evidence store .sbe/evidence it would review. A reviewer who writes the receipts it reviews is the defect reviewer separation exists to stop.

  2. The reviewer opens correctly instead, owning nothing:

    sbe task open: review-the-bundle is open. reviewer-1 (reviewer) owns 0 path(s): (none).

  3. The reviewer checks the agent's receipt, not the agent's word for it:

    python3 "$ROOT/bin/sbe" evidence verify /tmp/sbe-book-ch11-receipts/agent-1-receipt.json --cwd .
    NO-DATA  /tmp/sbe-book-ch11-receipts/agent-1-receipt.json
  the working tree was dirty or unreadable when this ran (2 uncommitted path(s)), so the receipt covers a state that was never committed and nobody else can reproduce. That is advisory, and advisory is NO-DATA here rather than a pass

  4. The reviewer reads sbe status before deciding. It exits 0 and reports nothing blocking, but says nothing about the row-count catch either, because nothing there wrapped that catch in anything the tool reads. sbe status reports what was recorded, in the places it knows to look; it was never built to be a second opinion on the change.

  5. The reviewer records a forced, honest close rather than pretending the bundle is clean (the same excerpt as journey stop 6 above): FORCED, never PASS.

Honestly: sbe pr verify <number> --repo owner/name is the real command for live GitHub pull request evidence. No chapter of the book runs it against a live pull request with captured output, so this tutorial uses the book's actual reviewer and status walkthrough rather than inventing one.

For developers

Co-writing code with it

Taking a task yourself starts the same way an agent's task does: bin/sbe task open --id <id> --agent <you> --role writer --base <commit> --verify "<command>" --owns <path> --cwd . opens the fence. Edit only the paths you declared. When you are done, bin/sbe task close <id> --cwd . reads the actual diff and reports PASS only when every changed path was inside the declaration.

It refuses to close what it cannot prove because closing does not take your word for what changed. A path you touched but never declared is reported as a VIOLATION, not a warning, and the close itself records that.

Where the file claims live: .sbe/tasks.json, the task registry. Every open task, its owner, its role, and its declared paths are read from that one file, not from memory or from a chat history.

Two habits keep the code modern and clean. First, small, single purpose modules: if a paragraph cannot say why a module exists, it is trying to be more than one thing. Second, no silently swallowed errors: the companion linter in tools/sbe_score.py names the file, the line, and the pattern, whether that is a bare except, an except that only passes, or a discarded subprocess result, rather than letting a wrong result pass for a right one.

Honestly not there yet

Some things worth knowing before you rely on this:

  • Not yet listed in any Claude plugin marketplace beyond this repository. A community marketplace submission packet is prepared and waiting on the product owner's final steps; the official directory is curated by Anthropic with no application process. Installing today still means running the two commands above, not clicking install in a store.
  • Claude Code is the only supported host today. Other AI coding tools are planned but not shipped.
  • Releases are not yet signed, and the current tag (a labeled release point) lags behind the main branch (the most current, actively developed version).
  • No outside beginner studies have been run yet.

BrotherSBE's own rulebook is what insists these gaps get said out loud this early. It would rather list them than let you find them the hard way.
